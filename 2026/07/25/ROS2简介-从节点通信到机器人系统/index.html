ROS 2 简介：从节点通信到机器人系统

发表于2026-07-25|更新于2026-07-25|机器人开发
|阅读量:

第一次接触 ROS 2 时，我把它理解成一个“装在 Ubuntu 上的机器人操作系统”。真正开始搭节点、看话题和调 Launch 文件后才发现，这个说法并不准确。ROS 2 不负责像 Linux 那样管理进程、内存和文件系统，它更像一套机器人软件开发框架：帮我们拆分功能、定义接口、组织通信，并提供调试和部署工具。

这篇文章是我阅读入门资料和官方文档后整理的一份阶段性笔记。重点不是列出所有命令，而是先回答三个问题：ROS 2 解决什么问题，各部分怎样连接，以及一个项目应该从哪里开始学习。

1. 为什么机器人需要 ROS 2

一台移动机器人通常同时包含摄像头、激光雷达、IMU、底盘、电机控制器和计算平台。软件侧还要完成驱动、定位、感知、规划、控制和人机交互。把这些逻辑写进同一个程序，短期看起来直接，后期却很难测试、替换和复用。

ROS 2 的基本思路是把系统拆成职责明确的节点。例如：

  • 相机节点只负责采集并发布图像；
  • 识别节点订阅图像，输出检测结果；
  • 定位节点融合里程计、IMU 和雷达数据；
  • 规划节点根据地图和目标生成路径；
  • 控制节点把速度指令转换成底盘动作。

这些节点可以运行在同一台计算机上，也可以分布在机器人本体、边缘计算设备和远程工作站中。只要接口一致，某个节点更换语言、算法或硬件时，其他模块不必全部重写。

ROS 2 名字里虽然有 Operating System，但它不是传统意义上的操作系统。更准确地说，它是客户端库、通信中间件、构建工具、可视化工具和机器人软件生态的组合。

2. 从应用节点到底层通信

ROS 2 的 API 看起来很简洁：创建节点、发布消息、订阅话题。实际数据会经过多层抽象，最后由中间件完成发现和传输。

最上层是我们编写的机器人功能节点。C++ 程序通常使用 rclcpp，Python 程序使用 rclpy。再往下，RCL 提供语言无关的基础能力，RMW 则把 ROS 2 接口适配到具体的中间件实现。

ROS 2 默认使用基于 DDS/RTPS 标准的通信体系。DDS 提供自动发现、数据序列化、发布订阅传输和 QoS 策略。对普通应用开发者来说，DDS 大多隐藏在 ROS 2 API 后面；但遇到节点发现失败、消息丢失或跨机器通信问题时，理解这一层会很有帮助。

ROS 2 不依赖 ROS 1 的中心 Master。节点可以通过中间件互相发现，这减小了单点故障风险。不过，“去中心化”并不意味着网络配置可以忽略：域编号、组播、防火墙和 QoS 不匹配仍会影响节点发现与通信。

3. 节点、功能包与工作空间

这三个概念很容易混在一起：

概念 可以怎样理解 主要内容
节点 Node 一个运行中的功能单元 发布、订阅、服务、动作和参数
功能包 Package 可构建、可复用的软件模块 源码、接口、配置、启动文件和依赖信息
工作空间 Workspace 管理一组功能包的工程目录 src、build、install 和 log

4. 四类交互方式怎样选择

ROS 2 初学阶段最重要的不是记住 API，而是理解不同数据应该采用什么交互方式。

话题：持续流动的数据

话题采用发布/订阅模型，适合图像、点云、里程计和传感器状态等连续数据。发布者不关心具体有哪些订阅者，订阅者也不要求发布者立即返回结果。

例如，相机节点可以在 /camera/image_raw 上持续发布图像，多个视觉节点同时订阅，各自完成目标检测、录像或可视化。

服务：快速完成的请求

服务是请求/响应模型，适合查询状态、重置计数器或执行一个很快结束的计算。调用方需要结果，但任务不应该长期占用服务端。

如果任务需要几秒甚至几分钟，并且可能取消，就不应该硬塞进服务。

动作：可反馈、可取消的长任务

动作由目标、过程反馈和最终结果组成。导航到某个位置、机械臂执行轨迹等任务都适合使用动作。客户端不仅能看到进度，还可以取消目标。

参数：节点的运行配置

参数用于保存节点配置，例如检测阈值、地图路径或控制频率。参数属于具体节点，不是整个 ROS 2 图中随意共享的全局变量。对于持续变化的业务数据，仍应使用话题或其他通信接口。

5. 接口定义让节点真正解耦

通信双方必须约定数据结构。ROS 2 常见的接口文件有三种：

  • .msg：消息定义，用于话题；
  • .srv：请求与响应定义，用于服务；
  • .action：目标、结果与反馈定义，用于动作。

接口的价值不只是“能传数据”。例如不同厂商的激光雷达，如果都发布 sensor_msgs/msg/LaserScan，导航节点就可以在不理解每款雷达寄存器和协议的情况下使用扫描数据。

设计自定义接口时，我认为有两个原则值得先记住：一是字段表达业务含义，不要暴露某个节点内部的数据结构；二是尽量使用已有标准消息，避免为同一种数据重复定义格式。

6. QoS：通信能否匹配的关键

ROS 2 允许通过 QoS（Quality of Service）描述通信要求。常见策略包括：

  • Reliability：可靠传输或尽力而为；
  • Durability：是否为后来加入的订阅者保留历史样本；
  • History 与 Depth：保存全部还是最近若干条消息；
  • Deadline、Lifespan、Liveliness：对时间和存活状态的约束。

传感器数据通常更重视“尽快拿到最新值”，允许偶尔丢一帧；控制指令或状态切换则可能更看重可靠性。QoS 并不是越可靠越好，重传和缓存都会带来资源与延迟成本。

一个常见现象是：话题名称和消息类型完全一致，却始终收不到数据。此时除了网络，还要检查发布端和订阅端的 QoS 是否兼容。

7. ROS 2 自带哪些工具

ROS 2 的优势不仅是通信，还有一套围绕机器人系统的工具链。

工具 用途
ros2 CLI 查看节点、话题、服务、动作、参数和接口
RViz2 可视化点云、图像、地图、轨迹和坐标系
rqt 提供节点图、曲线、日志等图形化插件
rosbag2 录制与回放话题数据，便于复现实验
Launch 同时启动多个节点并传入参数、重映射和命名空间
tf2 管理机器人各坐标系之间随时间变化的变换
URDF / Xacro 描述机器人连杆、关节、外观和碰撞模型

其中 ros2 node list、ros2 topic list、ros2 topic info 和 ros2 interface show 很适合排查“系统里到底运行了什么”。rqt_graph 则能直接看到节点与话题之间的关系。

8. ROS 2、实时性与嵌入式

ROS 2 提供了面向实时系统的设计基础，例如可选择的中间件、QoS 和执行器模型，但“使用 ROS 2”不等于程序自动获得硬实时能力。真正的实时系统还涉及实时内核、线程优先级、内存分配、回调执行时间和驱动行为。

对于资源有限的微控制器，通常不会直接运行完整 ROS 2，而是使用 micro-ROS，将 MCU 上的执行器、传感器和控制逻辑接入 ROS 2 网络。上位机负责感知与规划，MCU 负责确定性更强的底层控制，这种分工在移动机器人中很常见。

9. 版本应该怎样选

ROS 2 采用发行版机制。不同发行版绑定的 Ubuntu、Gazebo 和软件包版本并不完全相同，教程里的命令不能无条件混用。

截至 2026 年 7 月：

  • Lyrical 是最新正式发行版；
  • Jazzy 是支持周期较长的 LTS 版本，适合基于 Ubuntu 24.04 的新项目；
  • Humble 仍在支持期内，资料和现有项目较多，常见于 Ubuntu 22.04。

如果是长期项目，应该先看硬件驱动、Nav2、MoveIt 2 和仿真环境是否支持目标发行版，再决定升级，而不是只追求最新版本。

10. 我准备怎样继续学习

接下来我会按一个小型移动机器人系统来实践，而不是把每个工具孤立地学一遍：

  1. 用 turtlesim 熟悉节点、话题、服务和动作；
  2. 创建 C++ 工作空间与功能包，写一个最小发布/订阅节点；
  3. 用 rosbag2 录制数据，并在离线环境中回放；
  4. 接入相机或 D435i，在 RViz2 中观察图像、点云与坐标系；
  5. 编写 Launch 文件，把驱动、可视化和算法节点组合起来；
  6. 调整传感器话题的 QoS，观察可靠性和延迟变化；
  7. 最后再进入 tf2、URDF、Nav2 和 micro-ROS。

我目前对 ROS 2 的理解仍在通过项目验证。这篇简介先建立一张整体地图，后面的文章再记录节点编写、Launch、tf2 和实际传感器接入中遇到的问题。
